# 城市社区上门理疗 · 预约评估疗程结算平台

一个面向城市社区的**上门理疗**全流程平台：用户预约「颈肩腰腿痛理疗 / 术后康复 / 产后修复 / 老人关节训练」时先做**上门前健康风险评估**，康复师/理疗师接单前查看**风险边界与所需器械**，到场签到后记录疼痛评分、动作受限、生命体征、实际项目、器械、手法强度与反馈；评估、派单、上门、疗程、异常、随访、结算、复诊建议**全部沉淀在同一条健康服务记录**里。

> 核心原则（产品红线，已落到代码与页面）：
> 1. **健康风险在商业疗程之前**：高风险预约默认阻断派单，平台风控复核后才放行。
> 2. **理疗效果并非每次线性改善**：禁忌、疼痛变化、家属期待、技师能力共同决定「继续 / 暂停 / 终止 / 转诊」。
> 3. **三端看到不同的依据**：用户看到每次服务依据，技师看到风险边界，管理端看到异常与退款是否与服务质量有关，并据此优化派单。

技术栈：**Vue 3（Vite + Pinia + Element Plus）+ NestJS 10 + PostgreSQL 15**。

## 一、一键启动（Docker Compose）

前置：已安装 Docker / Docker Compose。

```bash
cd /workspace/188-a
docker compose up --build
```

启动后：

| 服务 | 地址 | 说明 |
| --- --- | --- |
| 前端（用户/技师/管理三端） | http://localhost:8080 | nginx 托管静态资源并反代 /api |
| 后端 API | http://localhost:3000/api | NestJS |
| PostgreSQL | localhost:5432 | 库名 physio，用户 appuser / apppass |

后端容器首次启动会**自动执行建表迁移并写入幂等种子数据**（`backend/migrations/001_init.sql`、`002_seed.sql`），无需手工初始化。重置数据：`docker compose down -v && docker compose up --build`。

> 本项目为全栈（含供用户完成业务操作的前端页面），按任务约定不强制提供 Swagger/OpenAPI UI；接口可用 `backend/scripts/smoke.mjs` 验证。

## 二、本地开发启动（不使用 Docker）

需要本机 PostgreSQL 15（或用任意 PG 实例，通过环境变量覆盖连接信息）。

```bash
# 1. 数据库（示例：使用本机 psql 创建）
createdb physio

# 2. 后端（端口 3000，启动自动建表+种子）
cd backend
npm ci
DB_HOST=127.0.0.1 DB_PORT=5432 DB_USER=<用户> DB_PASSWORD=<密码> DB_NAME=physio npm run start:dev

# 3. 前端（端口 5173，/api 自动代理到 3000）
cd ../frontend
npm ci
npm run dev          # 如后端不在本机：VITE_API_TARGET=http://后端:3000 npm run dev
```

后端环境变量：`DB_HOST / DB_PORT / DB_USER / DB_PASSWORD / DB_NAME / PORT / JWT_SECRET`。

## 五、功能验证方式（推荐操作路径）

1. **风险前置**：用陈秀兰（13800000004）登录 → 新建预约「老人关节训练」，填写冠心病/糖尿病/骨质疏松/无电梯 → 提交后看到高风险阻断，记录不会进入派单池。
2. **风控复核 + 智能派单**：admin 登录 → 风控复核与派单 → 放行 → 查看派单评分（刘康复因擅长、年资、异常率排第一；高风险单对低年资吴新手额外扣分）→ 指派。
3. **技师风险边界**：刘康复登录 → 待接单（按风险分排序，红标展示禁忌/器械）→ 确认接单 → 我的工单 → 到场签到 → 提交服务报告（高风险单弹窗默认限制手法强度≤4）。
4. **异常与结算**：报告中填写「理疗中不适」会自动生成高优先级异常；含疗程单提交后自动生成「医保/补贴/自费」分摊，渠道失败会进入管理端「医保/补贴结算」挂账列表，可一键重试并重算分摊。
5. **退款质量判定**：用户在记录详情申请退款 → admin 在「退款审批」判定**是否与服务质量有关**；判定结果计入技师质量异常率并影响后续派单评分（对比刘康复与吴新手的看板数据）。
6. **同一条记录**：打开任意记录详情，右侧/下方时间线按时间串联 评估→派单→上门→服务→异常→随访→结算→退款→复诊建议 九个阶段。

## 八、数据模型要点

- `service_records` 是唯一主线：`assessments / dispatch_logs / service_reports / incidents / follow_ups / settlements / refunds / revisit_recommendations` 均以 `record_id` 挂接，记录详情与时间线由它聚合。
- `courses` 疗程包按「单次折算价」结算，记录 `insurance_no / subsidy_rate`；`settlements` 分列医保、补贴、自费金额与渠道状态，失败可重试并重算。
- `incidents.quality_related` 与 `refunds.quality_related` 由管理端判定，是派单评分与异常率看板的输入；异常率口径为「发生异常的完工记录数 / 完工记录数」（不超过 100%）。
- 风险引擎规则可解释（年龄、疼痛分、既往病史、用药、禁忌、无电梯等逐条加分），分数、等级、标签、处置建议全部落库并向用户/技师/管理端三端展示。
